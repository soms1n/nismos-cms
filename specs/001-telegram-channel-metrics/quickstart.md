# Проверка: метрики аудитории Telegram-канала

Этот документ описывает проверку после реализации плана. Созданы pnpm workspace, приложение `apps/admin-telegram` и серверная Telegram-инфраструктура. Выполнены задачи T001–T011 из [tasks.md](tasks.md).

**Текущая точка остановки**: T012 не выполнен, поскольку реальный staging-канал и его секреты не настроены. T013–T028 и реализация US1 заблокированы до успешного feasibility spike.

## Продолжение реализации

1. Создать локальный файл переменных из шаблона:

   ```bash
   cp apps/admin-telegram/.env.example apps/admin-telegram/.env
   ```

   Файл `.env` исключён из Git. Не отправлять его содержимое в чат, логи или репозиторий.

2. Заполнить `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` для выделенного staging-аккаунта, затем выполнить интерактивный вход:

   ```bash
   pnpm telegram:login
   ```

   Скрипт запрашивает телефон, код и 2FA-пароль. По умолчанию сессия создаётся как `../nismos-cms-secrets/telegram.session` относительно корня репозитория. Существующий файл не перезаписывается. Можно передать другой путь вне репозитория аргументом `pnpm --filter admin-telegram telegram:login -- /абсолютный/путь/telegram.session`.

3. Самостоятельно перенести содержимое созданного session-файла в `TELEGRAM_SESSION` локального `.env` или менеджер секретов. Session string даёт полный доступ к Telegram-аккаунту.
4. Заполнить `TELEGRAM_CHANNEL`, независимо подтверждённые `TELEGRAM_EXPECTED_TOTAL` и `TELEGRAM_EXPECTED_DELETED`. Контрольный канал должен содержать удалённые аккаунты. Оставить `TELEGRAM_VERIFY_RUNS=20` или задать большее значение.
5. Выполнить `pnpm telegram:verify`. Скрипт сам читает `apps/admin-telegram/.env`, делает не менее 20 полных обходов и выводит только агрегированные счётчики, коды ошибок и длительности.
6. При успехе записать агрегированные результаты и измерения SC-002 в [research.md](research.md), отметить T012 в [tasks.md](tasks.md), затем продолжить T013–T014 и US1.
7. При ошибке конфигурации исправить окружение и повторить команду. При неполном обходе, неизвестных участниках, несовпадении контрольных счётчиков или нестабильных результатах не переходить к T013: остановить реализацию и вернуть спецификацию на уточнение.

В установленной версии `mtcute` документировано ограничение Telegram: через текущий запрос участников доступно не более 200 записей независимо от offset/limit. Шлюз отклоняет неполный обход; нельзя подменять его общим счётчиком канала или первыми 200 участниками.

## Предварительные условия

- Node.js 24 LTS и pnpm установлены.
- Создано приложение `apps/admin-telegram` и корневой pnpm workspace.
- Настроен OIDC/OAuth-провайдер; в allowlist добавлена пара `issuer + subject` тестового администратора.
- Для staging создан выделенный Telegram-аккаунт с 2FA. Он является участником и администратором канала и может просматривать участников.
- Telegram API ID, API hash и session string находятся в секретах окружения, а не в репозитории.
- Для spike известен контрольный набор участников, включая удалённые аккаунты, с независимо подтверждёнными ожидаемыми значениями.

Переменные окружения: `AUTH_URL`, `AUTH_SECRET`, `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `ADMIN_SUBJECTS`, `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, `TELEGRAM_SESSION`, `TELEGRAM_CHANNEL`.

## 0. Обязательный feasibility spike

**Команда после реализации скрипта**: `pnpm telegram:verify`.

**Сценарий**:

1. Подключиться выделенной staging-сессией к выбранному каналу.
2. Проверить доступность канала и право просмотра участников.
3. Выполнить полный постраничный обход пустым поисковым фильтром.
4. Сверить участников и удалённые аккаунты с контрольным набором.
5. Повторить обход при стабильном составе канала и проверить повторяемость.
6. Выполнить не менее 20 измерений длительности на реальном размере канала.

**Ожидаемый результат**: полный состав доступен, удалённые аккаунты классифицируются, неизвестные записи обнаруживаются, результаты повторяемы. Не более 5% успешных обходов превышают 5 секунд, если подтверждается SC-002.

**Блокирующий результат**: если полный обход или классификация недоступны, основную реализацию не продолжать; вернуть спецификацию на уточнение. Не заменять неполный результат общим счётчиком Bot API.

## 1. Отображение трёх показателей

**Given** тестовый Telegram-адаптер возвращает 1 000 уникальных участников, из которых 120 удалены.

**When** администратор открывает панель.

**Then** на одном экране отображаются `1 000`, `120`, `880` и `updatedAt`; выполняется формула `total = deleted + real`.

## 2. Ручное обновление

1. Открыть панель и зафиксировать прежний `updatedAt`.
2. Изменить данные тестового адаптера.
3. Нажать «Обновить».
4. Проверить, что все значения и timestamps заменены одним новым снимком.
5. Нажать кнопку несколько раз во время обхода и проверить, что выполняется только один обход.

## 3. Авторизация

- Запрос без сессии получает `401`, панель не раскрывает метрики.
- Аутентифицированный пользователь вне allowlist получает `403`.
- Удалённый из allowlist администратор теряет доступ при следующем запросе, даже если его прежняя сессия ещё существует.
- Ответы содержат `Cache-Control: no-store`.

## 4. Ошибки и неполные данные

По очереди смоделировать:

- ошибку на промежуточной странице;
- `FLOOD_WAIT`;
- превышение таймаута;
- `userEmpty`, `min` или отсутствующий объект пользователя;
- дубликаты и противоречивые счётчики;
- запрос обновления с другого origin.

**Ожидаемый результат**: частичный снимок не публикуется. При наличии прежних значений они явно помечены устаревшими; без прежних значений показано состояние недоступности. Секреты и данные отдельных подписчиков отсутствуют в ответах и логах.

## 5. Граничные значения

Проверить unit-тестами:

- пустой канал → `0 / 0 / 0`;
- все аккаунты удалены → `real = 0`;
- бот без `deleted=true` остаётся в `real`;
- большие счётчики отображаются точно;
- любой `unknown` отклоняет весь новый снимок;
- ошибка нового обхода не перезаписывает последний успешный снимок.

## 6. Staging smoke

1. Войти через реального OIDC-провайдера под разрешённым администратором.
2. Открыть панель и получить метрики реального канала.
3. Сравнить результат с последним подтверждённым spike.
4. Обновить вручную и проверить timestamp и состояние интерфейса.
5. Перезапустить приложение: прежний снимок исчезает, панель требует нового успешного обновления.

Staging-проверки не запускаются в обычном CI и не используют production-сессию.
