# Архитектура проекта

## Статус

Предложенная структура. Окончательные решения зависят от стека, списка административных приложений и архитектуры backend.

## Рекомендуемый подход

Использовать монорепозиторий с независимыми административными приложениями и общими пакетами. Каждое приложение должно отдельно разрабатываться, тестироваться, собираться и развёртываться.

Для TypeScript предлагаются pnpm workspaces и Turborepo. Микрофронтенды на начальном этапе не рекомендуются из-за дополнительной сложности сборки, авторизации и управления зависимостями.

## Структура репозитория

```text
nismos-cms/
├─ apps/
│  ├─ admin-users/          # Управление пользователями и доступом
│  ├─ admin-content/        # Управление контентом
│  └─ admin-settings/       # Системные настройки
│
├─ packages/
│  ├─ ui/                   # Кнопки, формы, таблицы, диалоги
│  ├─ auth/                 # Клиентская авторизация и проверка прав
│  ├─ api-client/           # HTTP-клиент, обработка ошибок, типы ответов
│  ├─ config/               # Общие настройки линтера и TypeScript
│  └─ testing/              # Общие тестовые утилиты и фикстуры
│
├─ services/                # Добавляется, если backend находится в этом репозитории
│  └─ api/
│
├─ infra/                   # Добавляется при появлении инфраструктурного кода
│  ├─ docker/
│  └─ deploy/
│
├─ docs/                    # Архитектурная и проектная документация
├─ specs/                   # Спецификации Spec Kit
├─ .specify/
├─ .kimi-code/
├─ package.json
├─ pnpm-workspace.yaml
├─ turbo.json
└─ README.md
```

На начальном этапе достаточно создать `apps/`, `packages/`, `docs/`, `specs/` и корневую конфигурацию. Каталоги `services/` и `infra/` следует добавлять только при появлении соответствующего кода.

## Структура отдельного приложения

```text
apps/admin-users/
├─ src/
│  ├─ app/                  # Инициализация, роутинг, провайдеры
│  ├─ pages/                # Страницы и маршруты
│  ├─ features/             # Бизнес-операции: создание, блокировка и т. п.
│  ├─ entities/             # Пользователь, роль, разрешение
│  ├─ widgets/              # Составные блоки страниц
│  └─ shared/               # Только локальные вспомогательные модули
├─ tests/
├─ public/
└─ package.json
```

## Правила

- Приложения не импортируют код друг друга.
- Код выносится в `packages/*` при появлении реального повторения, а не заранее.
- Общие пакеты не содержат бизнес-логику отдельных приложений.
- На первом этапе приложения используют единые версии общих пакетов внутри монорепозитория.
- Изменения общих пакетов проверяются тестами и сборкой всех зависимых приложений в CI.
- Каждое приложение может развёртываться на отдельном поддомене, например `users.admin.example.com`.
- Клиентская проверка прав используется только для интерфейса. Backend обязан самостоятельно проверять авторизацию каждой операции.

## Основной компромисс

Монорепозиторий уменьшает дублирование и упрощает совместные изменения, но изменения общих пакетов могут затрагивать несколько приложений. Поэтому общие пакеты требуют автоматических тестов и проверки зависимых приложений.

## Решения, которые ещё нужно принять

- Frontend- и backend-стек.
- Список первых административных приложений.
- Общий или раздельный backend для приложений.
- Способ аутентификации и модель ролей и разрешений.
- Схема развёртывания и адреса приложений.
